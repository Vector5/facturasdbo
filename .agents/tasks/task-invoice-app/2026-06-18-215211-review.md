# PIN-authenticated invoice management system (v2)

All nine issues from the v1 review have been addressed. CSRF tokens protect every state-mutating form. `sanitizeInput` no longer applies `htmlspecialchars` — escaping is now render-time only. The dead `sendInvoiceEmail` / `generateInvoicePdf` function calls are replaced with the class-based `InvoiceEmail` and `InvoicePDF` interfaces. Invoice numbers are regenerated server-side (ignoring the POST value), with `insertInvoiceWithRetry` handling the race condition via duplicate-key retry. The PDF download filename is sanitized with `preg_replace`. `session_regenerate_id(true)` is called post-login. Credential constants now carry clear `// CHANGE THIS` markers, and the SQL seed includes explicit instructions to replace the default PIN immediately.

**Watch for:** Error messages from PDO exceptions are rendered without `htmlspecialchars` in nueva-factura.php and editar-factura.php — a crafted column value or unusual MySQL error string could inject HTML into the admin page (confirmed). The `pdf_generado` flag in the database is never set to `1` after successful PDF generation, so the "PDF Generado" badge in ver-factura.php always reads "No" (confirmed).

**Verdict**: APPROVED

## High-level view

The security posture is now appropriate for a single-admin internal tool. CSRF protection uses a per-session synchronizer token validated on every POST handler, session fixation is eliminated via `session_regenerate_id`, and input handling follows the correct pattern of storing raw values and escaping only at render time. The only residual rendering risk is that PDO exception messages (which can contain user-supplied column data) flow into error arrays that are echoed without escaping.

Invoice creation no longer trusts the client-supplied `numero_factura`. The `insertInvoiceWithRetry` function regenerates the number server-side on each attempt and retries up to three times on duplicate-key violations, closing both the tampering and the race-condition gaps from v1.

One bookkeeping gap remains: `pdf_generado` in the database is never flipped to `1` after a successful generation, so the UI indicator in ver-factura.php is permanently stale.

## Unescaped exception messages in admin error display

Both `nueva-factura.php` (line ~110) and `editar-factura.php` (line ~102) build error strings by concatenating `$e->getMessage()`:

```php
$errors[] = 'Error al guardar la factura: ' . $e->getMessage();
```

These are later rendered:

```php
<li><?php echo $error; ?></li>
```

PDO exception messages can include interpolated query fragments or the literal column value that caused a constraint violation. If a client name contained `<script>` (now stored unescaped per the v1 fix), a subsequent duplicate-key or constraint error could reflect that value into the admin's browser. The page is behind authentication so exploitation requires either a compromised admin session or a self-XSS scenario, but the fix is trivial: escape at render time with `htmlspecialchars($error)`.

## Stale pdf_generado flag

The schema declares `pdf_generado TINYINT(1) NOT NULL DEFAULT 0`, and `ver-factura.php` renders a badge based on this column. However, no code path ever issues `UPDATE facturas SET pdf_generado = 1`. In `nueva-factura.php` the PDF is generated via `$pdfGenerator->generate($invoiceData)` after the INSERT, and in `editar-factura.php` it's regenerated on key-field changes, but neither updates the flag. The feature indicator is cosmetically broken: it always shows "No".
