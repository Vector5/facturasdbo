# PIN-authenticated invoice management system for warehouse rentals

A greenfield PHP 8 application covering the full lifecycle of warehouse-rental invoices: PIN-based admin login with IP lockout, CRUD with search/filter/pagination, optional PDF generation via DomPDF, optional email delivery via PHPMailer, and a public verification page. The application targets Hostinger shared hosting with Bootstrap 5 on the frontend and MySQL/PDO on the backend. Graceful degradation is the key design choice — DomPDF and PHPMailer are optional dependencies that produce warnings rather than failures when absent.

**Watch for:** CSRF protection is absent from every form — deletion, creation, and edit operations can be triggered from any origin (confirmed). The `sanitizeInput` helper double-encodes output because it applies `htmlspecialchars` on write *and* data is typically escaped again on render, which will produce visible `&amp;` artifacts (confirmed). The `reenviar.php` email resend path calls a `sendInvoiceEmail` function that is never defined anywhere in the codebase, making that feature dead code (confirmed). SMTP credentials and the default admin PIN hash are committed to version control in plain text (confirmed).

## High-level view

Authentication relies on a numeric PIN verified with `password_verify` against all admin records, combined with per-IP lockout after five failures. Sessions expire after 30 minutes of inactivity but are never regenerated after login, leaving a session-fixation window. There is no CSRF token mechanism anywhere in the application, so every state-mutating form is exploitable by a cross-site request.

Input handling uses a `sanitizeInput` function that applies `htmlspecialchars` at write time. Most templates then escape the output again, leading to double-encoding that corrupts displayed names and breaks LIKE-based searches. The `numero_factura` field in `nueva-factura.php` accepts the auto-generated value from a readonly input but doesn't server-side re-validate it, which could allow arbitrary invoice numbers via a tampered request.

The "resend email" feature (`reenviar.php`) calls a non-existent global function `sendInvoiceEmail` instead of using the `InvoiceEmail` class, so that button always silently fails. The `editar-factura.php` conditional PDF regeneration has the same problem with a non-existent `generateInvoicePdf` function.

The invoice-number generator queries by `LIKE` prefix and relies on `ORDER BY id DESC LIMIT 1` — safe for single-admin use but susceptible to a race condition under concurrency, resulting in a UNIQUE constraint violation and a confusing user-facing error.

<summary>Issues (9)</summary>

1. **No CSRF protection** — Every POST form (create, edit, delete, resend) lacks a CSRF token. Add a per-session token validated on each state-mutating request.
2. **Double HTML-encoding via sanitizeInput** — `sanitizeInput` runs `htmlspecialchars` before storage, then templates escape again on output. Store raw input (validated/trimmed) and escape only at render time.
3. **Dead resend path** — `reenviar.php` calls `sendInvoiceEmail()` which doesn't exist. Replace with the `InvoiceEmail` class already used in `nueva-factura.php`.
4. **Dead PDF regeneration in edit** — `editar-factura.php` checks `function_exists('generateInvoicePdf')` which is never defined. Use `InvoicePDF::generate()` instead.
5. **Credentials in version control** — SMTP credentials (app.php) and the default admin PIN hash (database.sql) are committed. Move secrets to environment variables or a `.env` file excluded from VCS.
6. **Invoice number tamperable** — `nueva-factura.php` trusts the POST value of `numero_factura` from a readonly input. Regenerate or validate it server-side before insert to prevent spoofing.
7. **Race condition in invoice number generation** — Two concurrent requests could generate the same number. Use a database sequence or `INSERT … ON DUPLICATE KEY` retry loop.
8. **PDF filename injection** — `descargar-pdf.php` uses the `numero_factura` value directly in `Content-Disposition` header without sanitizing characters that could break HTTP headers. Validate or strip special characters.
9. **Session fixation** — `index.php` never calls `session_regenerate_id(true)` after successful authentication. Regenerate the session ID post-login.

## CSRF gap across all forms

No form in the application includes a CSRF token. The delete action (`eliminar-factura.php`) checks `$_SERVER['REQUEST_METHOD'] === 'POST'` but that doesn't prevent cross-site form submission. An attacker who knows an invoice ID (predictable sequential integers) can forge a deletion or status change from any page the admin visits.

The `requireAuth()` call already guarantees a session exists, so a session-bound random token checked in a shared include is the straightforward fix.

## Double-encoding from sanitizeInput

```php
// includes/functions.php
function sanitizeInput(?string $input): string
{
    $input = htmlspecialchars($input, ENT_QUOTES, 'UTF-8');
    return $input;
}
```

This stores `&lt;`, `&amp;`, etc. in the database. Then every template does:

```php
<?php echo htmlspecialchars($invoice['nombre_cliente']); ?>
```

A client name like `O'Brien & Sons` becomes `O&#039;Brien &amp;amp; Sons` on screen. The current approach also breaks LIKE searches — a search for "O'Brien" won't match the stored `O&#039;Brien`.

## Broken resend and edit-regeneration paths

`reenviar.php`:
```php
if (!empty($invoice['email']) && function_exists('sendInvoiceEmail')) {
    $sent = sendInvoiceEmail($id);
}
```

No file defines `sendInvoiceEmail`. The function guard always fails, `$sent` stays `false`, and the user always sees the "send_error" flash message.

`editar-factura.php`:
```php
if ($keyFieldsChanged && function_exists('generateInvoicePdf')) {
    generateInvoicePdf($id);
}
```

No such function exists. The class-based `InvoicePDF` is the actual generator. Both paths are dead code from an earlier architectural draft.

## Session fixation and lockout topology

`index.php` sets session variables after PIN verification but never calls `session_regenerate_id(true)`. An attacker who can plant a session cookie (e.g. via a subdomain or HTTP response injection) can hijack the admin session after login.

The lockout counts failed attempts per `$_SERVER['REMOTE_ADDR']`. On shared hosting behind a CDN or reverse proxy, this may report the proxy IP, locking all users simultaneously. `X-Forwarded-For` handling may be needed depending on deployment.

## Invoice number generation race

```php
$stmt = $db->prepare(
    'SELECT numero_factura FROM facturas WHERE numero_factura LIKE :prefix ORDER BY id DESC LIMIT 1'
);
```

Between the SELECT and the INSERT, another request could generate the same number. The UNIQUE constraint rejects the second insert with a PDO exception, but the user sees a generic "Error al guardar" message rather than a graceful retry.

## Content-Disposition header injection

```php
header('Content-Disposition: attachment; filename="' . $filename . '"');
```

`$filename` comes from `$factura['numero_factura'] . '.pdf'`. If an attacker managed to insert an invoice number containing `"` or newline characters (possible if the invoice-number tamper issue is exploited), the HTTP response could be corrupted. A `preg_replace('/[^A-Za-z0-9\-_.]/', '', $filename)` filter is cheap insurance.

## Credentials and secrets in source

`config/app.php` contains placeholder SMTP credentials (`'tu_contraseña_smtp'`), and `database.sql` contains the bcrypt hash for PIN `1234`. The committed hash allows anyone with repo access to authenticate immediately after deployment if the admin doesn't change the default PIN. These should live outside version control in a `.env` file or environment variables.
